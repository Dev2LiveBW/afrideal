# Review, feat/order-payment-states, 2026-10-07

**Reviewed by**: Sonnet 5.5 (claude-sonnet-5-5), author model not stated
**Scope**: 54 files, branch vs main (the 12 files that arrived with the origin/main merge were not reviewed)
**Verdict**: Blocked

## Summary

The change makes an order start `AWAITING_PAYMENT` and routes every payment through `confirmPayment()` in the order claim, legs, finish, after. The signature handling, the display-only expiry helper and the AC-1/2/5/6/8 paths are well built and clearly explained. The recovery story is the weak point: the "finish" write is not a sound completion marker, and step 2 (supplier legs and payables) is a check-then-insert with no lock and with idempotency keyed on the wrong thing. That one hole produces duplicate supplier orders and payables under overlapping confirmations (Blocker), loses payables on resume, and cannot be healed by the finance path. Several refusal and edge paths also leave no record of money that moved, which matters at GA rigor.

Method note: findings come from reading the code and tracing interleavings by hand. I did not run the app. Postgres-only branches (the unique index, 23505) cannot be exercised by the JSON driver that `npm run verify` and CI use, and migration 0002 is not applied to Neon, so those findings (the reused-reference and FAILED-then-CONFIRMED ones) are by reading only. `tsc --noEmit` and `next lint` are clean.

## Blockers

### 🔴 Overlapping confirmations raise duplicate supplier orders and payables, `lib/payments/confirm.ts:310-399` (called at `:115`)
**Problem**: A replay deliberately continues into step 2 (`:112-115`, and the `claim = { payment: existing, wonClaim: false }` branch at `:109`). `raiseSupplierLegs` then reads the legs (`:311-322`), decides what is missing in memory (`:333`), and inserts later (`:395-396`). Nothing is held across that read and write, and `insertMany` only checks id uniqueness (`lib/db.ts:242-249`), not `(order_id, supplier_id)`. On Postgres, `nextIds` reserves disjoint blocks atomically, so two overlapping calls both mint fresh ids and both insert. The `claimPayment` lock only decides who owns the payment row; it does not serialise the legs. There is no unique index on supplier-orders or supplier-payables either.
**Why it matters**: Two callers reach step 2 for the same order when a gateway retries a callback that timed out while the first is still running, when a gateway sends the notification twice, or when two finance users mark the same order paid with the same reference. Result: two supplier orders (the supplier is told twice) and two payables of `amount: gross` each, so the ledger owes the supplier double. AC-3 and AC-4 ("exactly one", "creates no duplicate") and the spec's central claim fail in exactly the scenario the design exists for. The window is the length of step 2 (five reads, two id reservations, two transactions), longer from a slow link. Likelihood is moderate rather than high, but the harm is real money and silent.
**Suggested fix**: Make the existence check and the insert one atomic step per collection: compute "which suppliers already have a leg for these items" from the `rows` handed to the `mutate('supplier-orders')` callback and insert there, then do the same for payables inside `mutate('supplier-payables')` keyed on `supplier_order_id`. Add partial unique indexes as the database backstop (the spec already says both writes are "keyed by" those columns). Key the leg on the order's item ids, not on supplier id (see the next finding). Add a verify check that fires two callbacks concurrently.

## Major

### 🟠 A resumed run skips payables for legs that already exist, and the "legged" guard is dead code, `lib/payments/confirm.ts:320-333, 341, 367, 395-396`
**Problem**: Legs and payables are two sequential inserts. If the run dies or the second insert fails after the first, the next run sees the supplier in `alreadyLegged` (`:320`), drops it from `pending` (`:333`), and never raises its payable. The compensating check `if (legged.has(legId)) return` (`:367`) compares a freshly minted id against existing payables' `supplier_order_id`, so it can never be true. Keying legs on supplier id has two more consequences: if `resolveSupplier` picks a different supplier on resume (stock or status moved since), the same items get a second leg; and if ops reassigns a leg through the `supplier-orders` PATCH, a later replay re-raises a leg for the original supplier.
**Why it matters**: The spec and the file header promise an interrupted run "finishes its remaining work". Here the order still flips to PROCESSING at step 3, so a supplier is preparing goods for an order whose payable was never raised, and nothing flags it. Vercel function timeouts mid-flight make this reachable.
**Suggested fix**: Treat each leg and its payable as independent idempotent upserts. Per leg: find an existing leg covering these item ids (not by supplier), insert if absent. Per payable: find by `supplier_order_id`, insert if absent, including for legs that already exist. Delete the dead `legged` check once the real one exists. Add a recovery test that fails the payables insert once, then retries.

### 🟠 Finance cannot complete an interrupted confirmation, so bank transfer has no recovery path, `app/api/orders/[id]/route.ts:204-209`
**Problem**: After a crash between claim and finish, the state is a CONFIRMED payment on an AWAITING_PAYMENT order. `hasExpired` correctly treats that order as not expired, so `AwaitingPaymentQueue` still lists it with a "Mark paid" button. `MARK_PAID` then refuses with 409 "That order is already paid for" because it checks only "is there a CONFIRMED payment". The comment says "A race still converges, handled below", but nothing below handles it. `POST /orders/[id]/payments` also answers 409 "already paid".
**Why it matters**: The spec's recovery rests on "the next callback or a manual retry completes" it. For card, a gateway retry may do it. For EFT there is no gateway, only a human, and the human is blocked. The order stays "Waiting for payment" to the buyer indefinitely while money is recorded as received and supplier legs may already exist (see the CANCEL finding).
**Suggested fix**: In the pre-check, only refuse when the order is already at or past PROCESSING. When a CONFIRMED payment exists but the order is not finished, call `confirmPayment` with that payment's reference to resume. Cover it in verify by forcing the half-finished state.

### 🟠 `finishOrder` writes PROCESSING unconditionally, regressing later states, `lib/payments/confirm.ts:421-456`
**Problem**: The only guard is `if (current.status === 'PROCESSING') return` (`:432`). Any other status is overwritten, including IN_TRANSIT, DELIVERED and DISPUTED. A replayed callback (`confirmPayment` has no early exit for an order already past AWAITING_PAYMENT, `:84-138`) re-enters, finds the payment `sameReference`, finds all legs present, and still reaches `finishOrder`. The supplier-orders route advances the parent order as soon as legs exist (including in the window before step 3), so this is also what an interrupted run does to an order a supplier has already moved on. The same unconditional write also overwrites a CANCELLED/CUSTOMER order that landed after the `order` snapshot at `:85`.
**Why it matters**: A delivered order silently returns to PROCESSING with two new timeline entries ("Payment confirmed", "Sourcing from supplier"), customers see it un-delivered, and a DISPUTED hold is lost. The invariant "step 3 is the completion marker" only holds if step 3 never undoes later progress.
**Suggested fix**: Inside the `mutate('orders')` callback, only transition from AWAITING_PAYMENT or from CANCELLED with `cancel_reason === 'EXPIRED'`; for any other status return the row untouched and report "already finished". Have the caller skip `announce` when nothing changed (see the minor finding on replays).

### 🟠 `CANCEL` does not look at payments, `app/api/orders/[id]/route.ts:166-189`
**Problem**: The spec's API table lists "409 already paid" for CANCEL. The handler checks only `order.status`, so an order in the recoverable state (CONFIRMED payment, still AWAITING_PAYMENT, legs possibly raised) can be cancelled by the buyer. It then cancels the order's PENDING payables (`:173-176`) and sets `cancel_reason: 'CUSTOMER'`, after which `confirmPayment` refuses the order for good as `CANCELLED_BY_PERSON`.
**Why it matters**: Money received, supplier leg alive, payable cancelled, order cancelled, and the retry refused. Combined with the finance dead end above, the limbo state can last indefinitely, and the buyer is looking at a Cancel button for it.
**Suggested fix**: Refuse CANCEL (409 "already paid") when any payment for the order is CONFIRMED, checked inside a `mutate` so it cannot race a claim, and make the order write conditional on the status it read.

### 🟠 A reused bank reference silently marks a second order paid, `lib/payments/confirm.ts:100-110, 288-298`
**Problem**: The 23505 catch assumes the index fired because another call won the same claim. That cannot happen: `claimPayment` runs under the payments advisory lock and reads its invariants inside it, so a true race on one reference is impossible. What actually trips the index is a row the claim does not recognise. `findConfirmed` matches on `(provider, reference)` only, not on order. If finance types a bank reference that already exists on order A while marking order B paid (one transfer covering two orders is ordinary), the insert for B collides, `findConfirmed` returns A's payment, and B proceeds as a "replay": legs raised for B, B flipped to PROCESSING with A's reference, no payment row of its own, no amount check.
**Why it matters**: Breaks the invariant "no supplier order exists for an order with no CONFIRMED payment" and bypasses AC-11 for B. On the JSON driver there is no index, so dev and verify would instead create two CONFIRMED rows sharing one reference with no complaint; the two drivers disagree.
**Suggested fix**: After a 23505, only treat the row as a replay when `existing.order_id === input.orderId`; otherwise return a distinct refusal (reference already used on another order) and surface it to finance. Decide the product rule for one transfer covering several orders (per-order suffix, or include `order_id` in the index).

### 🟠 A confirmation arriving after a FAILED notice for the same reference becomes a permanent 500, `lib/payments/confirm.ts:258-263, 100-110`
**Problem**: The callback route finds the attempt by `(provider, reference)` in any status (`callback/route.ts:80-85`). `claimPayment` only flips a row whose status is STARTED. For a FAILED attempt it appends a new row with the same `(provider, reference)`, the partial unique index fires, `findConfirmed` finds no CONFIRMED row, and the original error is rethrown (`:108`). `handled()` returns it as a 500 carrying the SQL text.
**Why it matters**: Hosted gateways commonly fail an attempt (3DS timeout) and then succeed on the same session reference, and out-of-order delivery gives the same sequence. The customer is charged, the order never confirms, and the gateway retries a 500 indefinitely. Only the Postgres store shows it (no index on JSON), so verify and CI cannot see it.
**Suggested fix**: In the claim, treat a FAILED row with the same provider and reference as flippable (FAILED to CONFIRMED), and add that transition to the spec's payment state rules. Never return a raw driver error to the gateway.

### 🟠 Refused or dropped confirmations leave no record of money that moved, `lib/payments/confirm.ts:91-93, 112`; `app/api/payments/[provider]/callback/route.ts:76, 115-121`; `app/api/orders/[id]/route.ts:222-228`
**Problem**: `CANCELLED_BY_PERSON`, `ALREADY_PAID_DIFFERENTLY` (a double charge) and a stale callback all return 409 before any write. No payment row, no `audit()`, no `notify()`, not even `console.error`. The comment at `confirm.ts:89-90` says the caller "flags it for a human"; neither caller does.
**Why it matters**: A gateway calls back only after it took the money. These are exactly the cases that need a refund or a decision, and the application has no trace of them. That contradicts the spec's "audit logging on money transitions is not negotiable" and "refused, flagged" for GA. The 24h stale rule has the same effect after a gateway outage.
**Suggested fix**: Persist the refused payment as its own row (CONFIRMED with a flag, or a new REFUSED status) plus an audit entry and a notification to finance and super admins, then return 409. Do the same for stale callbacks that pass signature verification.

### 🟠 Late-payment detection misses the normal case, and finance has no UI to reopen an expired order, `lib/payments/confirm.ts:118`; `app/(admin)/admin/payables/page.tsx:41-46`
**Problem**: `wasExpired` is true only when the stored order is already CANCELLED with reason EXPIRED. The only code that writes that is the retry route (`payments/route.ts:46-64`); the confirm and mark-paid paths do not persist expiry, although the spec says they should ("the first time a payment path touches that order: a confirmation, a mark as paid, or a retry"). So: an abandoned order, then a card callback at minute 35 or an EFT on day 8, finds a stored AWAITING_PAYMENT order and confirms as an ordinary on-time payment, with no late note in the audit, timeline or notification (AC-7). Separately the finance queue filters on the effective status, so an expired order is not listed, and finance (who cannot reach `/admin/orders/[id]`) has no control to confirm the day-8 transfer that the spec names as its marquee trade-off.
**Why it matters**: AC-7's audit requirement fails for the usual route into it, and its recoverability exists only through a hand-written API call.
**Suggested fix**: In `confirmPayment`, compute lateness from the stored order and `windowHasClosed`, and persist the EXPIRED cancellation under the orders lock before reopening it, so the timeline and audit tell the story. List recently expired EFT orders in the finance queue.

### 🟠 Nothing can be paid in production as the branch stands, `app/(store)/checkout/CheckoutClient.tsx:25-33`; `lib/payments/adapters.ts:43-88`
**Problem**: The buyer-visible methods are DPO Pay, Orange Money and PayGate, and none has a gateway: with `PAYMENTS_PROVIDER` unset `startPayment` returns `redirectUrl: null`, and `mock` is refused when `NODE_ENV=production`. EFT, the path that is meant to let you trade before DPO approves, is accepted by the API but has no card in `GATEWAYS` (a code comment defers it to a later feature). Every order placed in production would sit at "Waiting for your payment" with a "Try paying again" button that cannot lead anywhere, then expire in 30 minutes.
**Why it matters**: Before this change checkout "worked" (falsely); after it, no buyer can complete a purchase. The spec lists EFT as the reason the feature is shippable first. This is a merge gate, not a code bug.
**Suggested fix**: Add the EFT card and its instructions screen to checkout (spec build task 9) before this reaches a deployed environment, or put checkout behind the pause switch until it does.

### 🟠 CI cannot pass `verify` as configured, and existing e2e journeys were not updated, `scripts/verify.mjs:120-143`; `.github/workflows/ci.yml:49-69`; `e2e/storefront/b-buy.spec.ts:57`
**Problem**: CI starts `npm start` (NODE_ENV=production) with no `PAYMENTS_PROVIDER`. `verify` orders with `ORANGE_MONEY`, so the attempt's provider is `ORANGE_MONEY`; `payCallback` then signs with the dev mock secret and posts to `/api/payments/ORANGE_MONEY/callback`. The server needs `PAYMENT_SECRET_ORANGE_MONEY`, finds none, and throws `MissingPaymentSecretError` (500) for both the "wrong signature" and the "signed callback" checks. Setting `PAYMENTS_PROVIDER=mock` instead makes every checkout fail with `MockProviderInProductionError`. The "154 passed" run therefore depends on a dev server with the mock enabled, which CI does not have. Separately, `b-buy.spec.ts` (B02) still expects the text "Order confirmed" after placing an order, which no longer renders for an unpaid order, and the merged `z01` journey has the supplier confirm an order straight after checkout, which now has no supplier leg.
**Why it matters**: Merging turns the verify job red (or forces a production-unsafe override), and the Playwright buying journeys break.
**Suggested fix**: Decide how automated runs pay: either allow the mock behind an explicit non-production opt-in that CI can set (a deliberate `ALLOW_MOCK_PAYMENTS` rather than NODE_ENV), or give verify and e2e an EFT path with a finance mark-as-paid. Update B02 and Z01 to place, pay, then continue.

## Minor

### 🟡 Dashboard "Recent orders" shows the stored status, so an expired order reads AWAITING_PAYMENT, `app/(admin)/admin/dashboard/page.tsx:144, 290`
Every other admin surface uses the effective status, but this list and its badge use `orders` directly. AC-5 says "CANCELLED on every surface". Pass the list through `allAsDisplayed`.

### 🟡 The AC-11 flag is not visible to finance, and the callback path accepts a shortfall quietly, `lib/payments/confirm.ts:96, 480-487`
`amount_matches` is stored, and the words "needs finance" go into one audit detail string. Nothing lists mismatched payments, nobody is notified, and `amount_matches` appears in no UI. For a signed callback with a short amount the order still goes to PROCESSING and the supplier is asked to prepare it. The spec's follow-up acknowledges "who chases it" is open, but at least a notification and a list are needed for the flag to mean anything. Related: the callback's `currency` is required (`callback/route.ts:36`) but never compared, so a signed `USD 100` matches a BWP 100 order, and `amount` allows negatives.

### 🟡 `announce` runs on every replay, so audit and customer notifications duplicate, and supplier notification is tied to who created the legs, `lib/payments/confirm.ts:121-129, 489-501`
Each replayed callback writes another `PAYMENT_CONFIRMED` audit entry with identical text and another "Payment confirmed" notification. On a resumed run `raised` is empty (the legs exist), so suppliers are never told about the paid order. Step 4 also sits outside the completion marker: a crash between finish and audit leaves a paid order with no audit entry, and a finance retry is refused (see the MARK_PAID finding). Make announcements idempotent per payment id (for example record `announced_at` on the payment) and notify suppliers for every leg not yet announced.

### 🟡 Persisting expiry in the retry route is an unconditional stale write, `app/api/orders/[id]/payments/route.ts:46-64`
`update('orders', ...)` merges `status: 'CANCELLED'` with a `timeline` built from the earlier read. If a confirmation finishes between that read and the write, a paid order is flipped to CANCELLED/EXPIRED with its legs live, and a concurrent timeline append is lost. Use `mutate('orders')` and re-check status and payments inside it.

### 🟡 Re-selected supplier keeps the original supplier's cost, and the item still names the original, `lib/payments/confirm.ts:343-365, 407-418`
When `resolveSupplier` re-routes a line, `supplier_subtotal` and `platform_margin` are computed from `item.supplier_cost` (the first supplier's offer), `OrderItem.supplier_id` is not updated, and the admin order page maps items to legs by `item.supplier_id` (`orders/[id]/page.tsx:221`), so the new supplier's line renders as a raw id. `selection_reason` is also derived from the first item only. AC-9 requires the customer price to stay fixed, not the cost basis to go wrong.

### 🟡 Checkout leaves an orphan order if `startPayment` throws, and its settings read is not fail-safe, `app/api/orders/route.ts:195-201`; `lib/payments/adapters.ts:97-100`; `app/(store)/orders/[id]/page.tsx:27`
The order and its items are inserted before `startPayment`. `providerFor` throws `MockProviderInProductionError` in a misconfigured production, and `bankTransferInstructions` throws if the settings read fails, both leaving an AWAITING_PAYMENT order with no payment. `checkoutIsPaused` fails open by design; the EFT instruction readers do not, and the order page 500s for an unpaid EFT order if the table is missing. Resolve the provider and instructions first, or catch and degrade to "details will follow".

### 🟡 EFT orders always leave an orphan STARTED row, `lib/payments/confirm.ts:258-263`
The STARTED row carries `provider_reference = order.reference`, but finance confirms with the bank's reference, so the row is never matched and a second row is appended. The comment says the code avoids exactly this orphan. Either match EFT STARTED rows regardless of reference, or close the STARTED row on confirmation.

### 🟡 `amount_matches: false` on STARTED and FAILED rows, and `Payment.amount` changes meaning, `app/api/orders/route.ts:211`; `types/index.ts:291-294`
The type says "False needs a human", yet every unconfirmed attempt is created with `false`, so any report filtering on it lists all open attempts. The type also says `amount` is "what we expected", but the claim overwrites it with what the provider reported. Make the flag nullable (meaningful only when CONFIRMED) and keep expected and received separate.

### 🟡 Unauthenticated probing, `lib/payments/signature.ts:45-54, 81-83`; `app/api/payments/[provider]/callback/route.ts:50`
`secretFor` runs inside `verifyCallback`, but only when a signature header is present. An unconfigured provider with a header answers 500 with `No signing secret for DPO_PAY. Set PAYMENT_SECRET_DPO_PAY...` (via `handled`), while a missing header answers 401, so a caller can learn which providers are configured and the env var names. Check for a configured secret and return the same vague 401. Also: `isStale` accepts a future `occurred_at`, the body is read with no size cap, and there is no rate limit (an unsigned request is cheap and never touches the database, which is good).

### 🟡 Payment details are returned to roles that should not see them, `lib/queries.ts:38-70`; `app/api/orders/[id]/route.ts:25-31`
Adding `payments` to `OrderDetail` sends every attempt (provider reference, amount, `note`, `failure_reason`) to the supplier role in `GET /api/orders/[id]`, and finance's internal note ("Underpaid, chasing the balance") to the buyer. Strip `payments` for suppliers and the staff `note` for customers. (`payables` leaking across suppliers in the same response predates this change.)

### 🟡 Pause does not stop new payment attempts on existing orders, `app/api/orders/[id]/payments/route.ts`
AC-8 is met literally (`POST /api/orders`), but "stop taking money during an incident" is not: the retry endpoint and the callback keep working. The pause card says "nothing already placed is affected", so this may be intended; confirm and document it.

### 🟡 Config and docs gaps, `.env.example`; `lib/payments/signature.ts:45-54`
`.env.example` lacks `PAYMENTS_PROVIDER`, `PAYMENT_SECRET_*` and `PAYMENT_WINDOW_SECONDS`, which the spec lists as required. The code reads `PAYMENT_SECRET_${provider}` (so `PAYMENT_SECRET_DPO_PAY`) while the spec names `PAYMENT_SECRET_DPO`; whoever wires DPO from the spec will hit the missing-secret error. The spec's migration phase 2 (backfill of live orders: synthetic payments, PENDING to AWAITING_PAYMENT) has no script, so on live data legacy PENDING orders never expire and still count as billable; if production data will simply be reseeded, record that decision in the spec.

## Strengths

- The signature path is built right: raw body read first, per-provider secrets, `timingSafeEqual` on equal-length buffers, a deliberately vague 401, and no database access before the signature, parse and staleness checks pass.
- `lib/payments/status.ts` really is display only. I grepped every importer: none is on a write path, and the file explains why (a write path that saw the effective status would refuse a real payment as a deliberate cancellation). `hasExpired` also correctly keeps a paid-but-unfinished order from showing as cancelled.
- `claimPayment` reads its invariants inside the same lock that writes, returns tagged outcomes rather than exceptions, and flips the opened STARTED row instead of orphaning it (for card references).
- The 23505 unwrapping (`error.cause.code`) is a good catch for drizzle 0.45, and the mock-in-production guard fails loudly rather than falling back.
- The seed asserts AC-2 both ways (no legs for an unpaid order, no payment row for it) and refuses to stamp CONFIRMED payments on orders that were never paid, which respects the Data Protection Act point in the spec.
- Comments explain why, not what, throughout, and `verify` drives the real signed callback instead of reaching into the store.

## Test coverage

Covered by `npm run verify` (JSON driver, dev server): unpaid start state, no legs or payables before payment, unsigned and wrongly signed callbacks refused, one signed confirmation, one sequential replay adding nothing, expiry reads on the two seeded orders, the analytics exclusion, MARK_PAID role gate and mismatched-amount flag, the retry endpoint's ownership and reuse, pause and resume. Typecheck and lint are clean.

Not covered, in addition to AC-7, AC-9 and the failed state already known: concurrent confirmations (the Blocker); recovery after a failed or partial step 2 (the spec's own "Recovery" scenario); replay after the order has progressed; CANCEL and its interaction with a CONFIRMED payment; the CANCELLED_BY_PERSON and ALREADY_PAID_DIFFERENTLY refusals and their codes; the stale-callback path; reused or colliding references; the Postgres-only 23505 and FAILED-then-CONFIRMED paths (the JSON driver has no index, so these branches have never run, and migration 0002 is not applied to Neon); payable amounts after confirmation (the old "invoices sum to the order subtotal" assertion was removed and not re-added); "no write happened on the read" for AC-5; and the dashboard surface. Existing Playwright journeys B02 and Z01 assume an order is paid at checkout and were not updated, and CI's verify job is not configured to be able to pay (see the Major above).
